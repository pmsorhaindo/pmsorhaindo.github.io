Safety nets for refactoring multi-stage LLM pipelines

An overnight lab note, October 2026. It comes with a small runnable toolkit, llm-pipeline-safety-kit (Python, MIT, 57 passing tests, runs offline).

TL;DR

A typical "answer questions about this data" assistant is a chain of LLM stages: a guardrail, a feasibility check, intent classification, a summariser checked by an evaluator with retries, a style pass that streams tokens, and follow-up suggestions. Refactoring that chain, or just editing its prompts, breaks things in three predictable ways:

  1. Vocabulary drift. The same stage has a graph node id, a prompt-store key, a code constant, event names and front-end handlers. A rename that misses one layer often fails silently, for example a prompt lookup that falls back to a default.
  2. Quality regressions. A prompt or model change makes answers subtly worse, most dangerously by inventing numbers. An evaluator that never sees the source data cannot catch that.
  3. Behaviour drift in the stream. Moving orchestration code changes the order, names or payloads of the events the client depends on, and the change is invisible until a user sees it.

The kit has one cheap, offline check for each problem: a stage contract, golden-case evals with a deterministic numbers-grounding check, and event-stream snapshot tests. Adopt them in this order: characterise → contract → golden evals → refactor.

1. Why these three safety nets

Net Protects against Why it's cheap Why a normal unit test isn't enough
Characterization snapshot of the event stream Accidental behaviour change while moving code Records what the system does today, so you don't have to write a spec first Unit tests check pieces; the client depends on the sequence of events
Stage contract (one YAML file) Renames that miss a layer; dead or stale prompt keys; client handlers for events that no longer exist Static: parses files, no runtime needed, runs in milliseconds Identifiers live in different languages and stores that no single test suite covers
Golden-case evals Prompt and model regressions; a lenient evaluator; wrong retry or fallback paths Deterministic checks plus recorded LLM responses mean no API calls in CI LLM output is not exactly reproducible, so you assert properties instead of strings

These nets are layered. The snapshot says what changed in the stream. The contract says which layer is out of step. The evals say whether the answers are still acceptable. None of them needs a real model call to run in CI, which is what makes them stick in a team that is busy shipping.

The one check worth stealing even if you take nothing else

numbers_grounded: extract every number in the answer (€1.25M, 1,250,000, 3.1%, 480k) and require each one to match a value in the input at the precision written, or a simple derivation of input values (difference, percent change, ratio, total). It is deterministic, takes about 100 lines and catches the most damaging failure of a data summariser. Put it inside the evaluator stage as well as in the evals, so a lenient evaluator model can't wave a hallucinated total through. One of the bundled golden cases proves exactly that: the evaluator model is scripted to say "looks great", and the candidate is still rejected.

One more lesson from the demo: the style pass runs after the evaluator. If it rewrites numbers, nothing downstream notices. The demo_failures suite shows this case. Either re-check grounding after styling, or make the style prompt structurally unable to change numbers, for example by masking them as placeholders before the pass and restoring them afterwards.

2. Adopting them in a legacy codebase (strangler order)

The aim is to put nets under the code before you move it, starting with the net that needs the least understanding of the code.

Step 0: Inventory (half a day)

List every identifier each stage is known by, in every layer: config/graph files, prompt rows (per environment), code constants and enums, emitted event names, front-end handlers, analytics and alerting strings, and anything persisted (stored conversation metadata, event logs). That table is the first draft of your contract.

Step 1: Characterise (1–2 days)

  • Capture real streams for 5–10 representative requests (happy path, retry, blocked, infeasible, a follow-up turn). If the orchestrator can't be called from a test, curl -N the endpoint against a fake or recorded model and save the raw SSE.
  • Normalise away what legitimately varies (ids, timestamps, durations, token chunking) and commit the snapshots.
  • Make the LLM client injectable if it isn't already. This is the single most valuable seam in the codebase.
  • Don't fix anything yet. If a snapshot captures a bug, leave it and write it down. Characterization tests pin current behaviour, not correct behaviour (Feathers).

Step 2: Contract (1 day)

  • Write contract.yaml from the inventory. Point sources at the real files.
  • Start lenient: use mode: within for consumers (clients only listen for known events) and covers for stores (extra legacy prompt rows are allowed). Fix or document every finding, then tighten to exact.
  • Export prompt-store keys from each environment and check them too. Environments drift apart more than code does.
  • Add it to CI. From now on every rename touches the contract first, and CI tells you which layers you missed.

Step 3: Golden evals (ongoing)

  • Seed with the snapshot scenarios plus one case per past incident. Every bug report becomes a case.
  • Use recorded responses per stage to force the paths that are hard to trigger: evaluator rejects then accepts, three rejections then fallback, guardrail blocks.
  • Prefer deterministic assertions (grounded numbers, word budget, required entities, verdicts, attempt counts). Add an LLM judge only for qualities you can't express otherwise, and calibrate it against your own labels first (Shankar et al.).
  • Run two tiers: an offline gate on every PR (fake or recorded LLM, must pass), and a nightly live run against the real model that reports pass rates over N repeats instead of blocking.

Step 4: Refactor behind the nets

  • Make small extractions. After each one, snapshots, contract and evals must all stay green.
  • For renames of anything persisted or shared across services, use parallel change (expand → migrate → contract). Emit or accept both names, migrate the consumers, then remove the old name. The contract can hold both names during the transition (events: [suggestions_ready, suggestions_generated]) with a note.
  • For bigger moves, run the new orchestrator next to the old one (strangler fig): send shadow traffic, compare normalised streams with the same snapshot normaliser, then switch over one page or use-case at a time.
  • Only re-record a snapshot when the diff is the change you meant to make, and say so in the PR.

3. Naming and ubiquitous language

Most pipeline drift starts as a naming problem. Some rules that pay off:

  1. One concept, one name, in every layer. If the stage is summarise, the node id, prompt key, enum, metric label and event prefix should all be recognisably summarise. Pick a spelling (UK/US) and let the contract enforce it. summarise/summarize drift is a real and common bug.
  2. The contract file is the glossary. Give every stage a one-line description and add the forbidden synonyms as comments. Code review then has something concrete to point at.
  3. Names that are persisted are API. Event names written to a conversation store, prompt keys in a database and analytics event names outlive the code. Rename them only with read-both or write-both migrations.
  4. Name by role, not by history. If the "override" prompt is the one always used, it is the prompt and not an override. If a field called history only holds user messages, call it user_messages, or carry roles explicitly. Misleading names cause real bugs, not just confusion.
  5. One verdict shape for every check stage. Use {passed: bool, reason: str} for guardrail, feasibility and evaluator alike. Mixing feasible, ok, valid and safe invites inverted-boolean bugs.
  6. Don't reuse safety words for non-safety outcomes. A parse failure isn't "unsafe". Keep blocked, infeasible and fallback as distinct statuses, so dashboards and alerts mean what they say.
  7. Namespace events by origin. If two services emit events into one stream, give each a prefix, so a reader knows who to blame and a grep finds the producer.
  8. Avoid overloaded product words in code. Words like dashboard, summary or report often mean a page, a feature, a stage and a stored artefact all at once. Give each meaning its own term in the glossary.
  9. Graph node ids are implementation details. Don't let callers outside the orchestrator depend on them. Expose stage names instead, and map them inside.

Legacy code and safe change * Michael Feathers, Characterization Testing, the idea behind snapshotting current behaviour before you change it. * Characterization test (Wikipedia), a short definition with references. * Martin Fowler, Strangler Fig Application. * Danilo Sato, Parallel Change (on martinfowler.com), the expand/migrate/contract pattern for renames. * Approval Tests and syrupy, mature snapshot testing libraries.

5. The toolkit

llm-pipeline-safety-kit.zip. Requires Python ≥ 3.9 and PyYAML.

psk contract examples/sales_assistant/contract.yaml    # finds the 4 planted drifts, exit 1

psk eval examples/demo_failures                        # shows failure output, exit 1
psk sse compare examples/sales_assistant/capture.sse examples/sales_assistant/snapshots/capture.json
Module What it does
contract.py YAML source of truth; structured / regex / lines sources; exact / covers / within modes; "did you mean" hints
evals.py YAML golden cases, scripted per-stage LLM responses, built-in and custom checks, LLM-judge hook, table / markdown / JSON / JUnit reports, exit codes 0/1/2
numbers.py Number extraction and grounding with rounding, %, k/M/B and derived values
sse.py + pytest plugin SSE parse and format, normaliser, sse_snapshot fixture, --update-snapshots
llm.py FakeLLM, record/replay CassetteLLM, optional OpenAI-compatible client via PSK_LLM_* env vars
demo_pipeline.py A reference six-stage pipeline (sales dashboard assistant) to run the examples against

Known limits: derived-number matching trades strictness for fewer false alarms, so turn it off (allow_derived: false) for high-stakes figures. The contract checker matches identifiers, not semantics. The demo pipeline is deliberately simple and is not a framework.
